# Nonzero ASIC version known answer

This is synthetic public test data, not a Bitcoin block, pool job, hardware
capture, or proof of mining. No owner inputs were used.

The 80 header bytes in `fixture.json` were independently assembled outside the
Rust builders: literal little-endian version `0x20406004`, previous-hash bytes
`00` through `1f`, merkle bytes `20` through `3f`, little-endian time `0x65010203`,
compact bits `0x1d00ffff`, and nonce `0x12345678`. ASIC response version bytes
`02 03` represent `0x00406000` after the prescribed 13-bit shift; OR with the
transmitted base version `0x20000004` yields the literal header version.

Python standard-library `struct.pack` and `hashlib.sha256` produced the fixed
header and digests. An independent command invocation confirmed SHA256d:

```sh
openssl dgst -sha256 -binary HEADER.bin | openssl dgst -sha256
```

The result is
`67dfaeb3b4bb6ab4b0ab13aa9b6abb8b9b3263c5b9ee034056e8434fddd861bb`.
The checked-in expected header and digest are constants, never regenerated by
the function under test. The 82-byte work payload follows the pinned
`BM1366_job` layout; the response's CRC5 residue was computed independently
with polynomial `x^5 + x^2 + 1`, initial register `0x1f`, MSB-first, and zero
final residue. The route test passes this fixed response through the actual
parser, dispatched-work registry, SHA256d reconstruction and pool qualification.

## Software-expected ticket filter

Pinned reference breadcrumbs:

- `reference/esp-miner/components/asic/asic_common.c:get_difficulty_mask`
- `reference/esp-miner/components/asic/bm1366.c:BM1366_init`
- `reference/esp-miner/components/asic/include/bm1366.h:BM1366_job`
- `reference/esp-miner/components/stratum/mining.c:test_nonce_value`
- `reference/esp-miner/components/stratum/utils.c:truediffone`

The configured nominal mask value 256 yields eight ticket-mask bits:
`(1 << floor(log2(ceil(256)))) - 1 = 0xff`. Per-byte bit reversal gives mask
bytes `00 00 00 ff` for register `0x14`.

Profile `bm1366-ticket-256-leading-zero-40-v1` explicitly assumes the software
model's implicit 32-bit baseline plus those eight ticket bits. For raw SHA256d
bytes interpreted as a little-endian integer `H`, the exact predicate is
`H < 2^216`: bytes 27 through 31 must all be zero. The last accepted integer is
`2^216 - 1`; `2^216` is rejected. No floating-point comparison implements this
predicate.

Bitcoin difficulty-one uses `D1 = 65535 * 2^208`. Thus nominal Bitcoin
difficulty 256 requires `H <= 65535 * 2^200`, a stricter boundary. At the
excluded ticket boundary `H = 2^216`, Bitcoin difficulty is exactly
`255.99609375`; floating-point rounding cannot safely distinguish this boundary
from the immediately preceding integer. The tests include the interval that
passes the software filter while missing the nominal difficulty-256 target.

This model is an observational expectation, not register readback, silicon
qualification, or a submission gate. The synthetic nonzero-version hash misses
it. A separate existing upstream-derived difficulty-about-683 reference candidate
checks that a filter match can still be below a pool target of 1000; it is not
represented as a new real-device result.
