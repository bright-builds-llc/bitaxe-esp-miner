# Upstream review: `c1915b0a` to `v2.15.4`

This review classifies every upstream commit between our pin and the latest
stable release, and maps each one to checklist rows. It belongs to
`task-parity-upstream-pin-refresh`.

It changes no checklist status, and the pin has not moved. Every `verified` row
still means `c1915b0a`.

`v2.15.4` left `master` at `b050903` (2026-08-20). Its 59 commits are 51 shared

## How this was checked

- Three reviewers read the 36 firmware commits against our source, and I read
  the 23 UI and docs commits. Large UI commits were judged from their messages
  and file lists.
- I rechecked these findings in the source myself: the access gate, the TLS
  pool selection, the `BM1370_init` changes, the register read addressing, the
  seeded defaults, 690 MHz, the new NVS keys and routes, the reset order, the
  Wi-Fi settings and the hidden text.
- Everything else here rests on one reviewer's reading. Nothing was built or
  run from upstream, no hardware was used, and no finding was observed on a
  device.

## Problems that exist at the pin too

These do not depend on moving the pin.

1. **The HTTP access gate does not check the peer address.** It is read from
   source, not yet observed on a device.
   - With `CONFIG_LWIP_IPV6=y`, ESP-IDF's server listens on `PF_INET6`, so
     `lwip_getpeername` returns a `sockaddr_in6`.
   - `maybe_peer_ipv4` (`firmware/bitaxe/src/http_api/access.rs`) passes a
     16-byte `sockaddr_in`. Its `sin_addr` overlays `sin6_flowinfo`, which is
     zero, so the peer always reads as the unspecified address.
   - `is_access_allowed` (`crates/bitaxe-api/src/route_shell.rs`) then checks
     only the Origin, and a missing Origin is allowed. A test pins this, and a
     comment there treats the zero address as an ESP-IDF quirk.
   - A failed peer read takes the same path.
   - Upstream reads the mapped address from `sockaddr_in6`, denies non-private
     peers and fails closed. So a public peer that can reach the device, through
     a port forward for example, can use settings and OTA on ours but not on
     upstream.
2. **A TLS primary pool silently diverts to the fallback pool.** It is read from
   source, not run. `read_pool_configuration` treats a pool with TLS set as not
   configured, and `maybe_preferred` then picks a plain fallback. Upstream would
   connect to the primary. I did not check what status the device reports.
3. **The 205 holds ASIC reset late.** Upstream holds it low early at both
   commits. Our 601 does too (`hold_asic_reset_early`), but the 205 first drives
   the line in `run_boot_gate_with_peripherals`, after NVS, settings, BAP and
   I2C. Whether the undriven line matters electrically is unknown.
4. **Network settings differ from upstream at both commits.** Upstream sets
   `btm_enabled` and `rm_enabled` on the station and allows 20 open sockets. Ours
   sets neither and allows 7. NET-001 and API-004 do not mention this.

## Owner decisions

Decided on 2026-10-30:

- **ESP-IDF 6 (`4cd2fb4`): upgrade, as upstream did.** Upstream is on 6.0.2 and we
  are on v5.5.4. The visible differences are `idfVersion` and possibly Wi-Fi and
  display behaviour, which were not assessed. Partition layout does not change.
  `task-esp-idf-6-upgrade` owns it.
- **BLE provisioning (`d1a9d3e`): in scope, with more security than upstream.**
  Upstream starts it 5 s after boot in AP mode. Its write characteristics carry no
  encryption or authentication flags, and they accept Wi-Fi and pool credentials.
  We have Bluetooth off. `task-secured-ble-provisioning` owns it.
- **New hardware (`3cfc082`, `cc667af`): documented and deferred.** See
  [the deferred boards](../../hardware/deferred-upstream-boards.md).
- **Unified firmware (`00eb2ef`): embed our own UI variants.** ADR-0034 still
  forbids bundling Angular AxeOS. `task-upstream-v2154-unified-firmware` owns it.

## Image size limits this work

Our app has to fit a fixed 4 MiB slot. Images built on 2026-10-29 leave 3,056
bytes free on the 205 and 44,800 bytes on the 601. BLE, TLS, mDNS, an embedded UI
and possibly ESP-IDF 6 all need more than that.

Upstream's partition table has the same slots, and an ordinary update cannot
safely change ours. So `task-firmware-image-headroom` has to come before those
features.

## Notes for later work

- **CA trust store (`d212a0f`).** This is the only change `v2.15.4` makes over
  `v2.15.3`. It replaces ESP-IDF's bundle with a pinned Mozilla-derived store
  after the eMudhra compromise, and upstream uses it only for Stratum TLS. We have no
  TLS client, and a reviewer found the bundle discarded at link time in both
  production images, so nothing is exposed today. `sdkconfig` still selects the
  ESP-IDF bundle, so `task-parity-stratum-tls` must use the replacement.
- **WPA2/3 compatibility (`0da3a22`).** Its flag does not exist on v5.5.4, and a
  reviewer found no RSNO client support there, so this cause should not apply.
  No router was tested.
- **Hidden text.** Four log strings at the target contain runs of zero-width
  characters that decode to `bitaxe`: `main/system.c:177`,
  `components/asic/bm1368.c:281` and `components/asic/bm1370.c:338` and `:374`.
  The pin has none and neither does our source. They do not affect logic, but
  copying those strings would carry them, so write ours independently.
