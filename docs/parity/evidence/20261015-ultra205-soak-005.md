The recent-worst values reset on device-uptime minute boundaries. That matches
the tracker's current-plus-previous-minute window, so a long send stays
visible for 60–120 s.

## Findings from the independent review

- `wifiRssi` is read only when Wi-Fi connects (`wifi_adapter.rs`), so it is
  constant for a whole run. It cannot show a dip during a stall. Upstream reads
  RSSI live on every system-info request (`system_api_json.c`), so this is
  also a parity gap. Follow-up: `task-parity-wifi-rssi-live`.
- Soak samples do not carry the send counts or the lifetime worst, so the
  counters' progress cannot be cross-checked directly. Follow-up:
  `task-soak-sample-send-counters`.
- Only the send calls are timed. A stall elsewhere on the server task, such as
  handler work, lock waits or receive, would show low send durations.
- A clean-jobs refresh at about 60 s active (`stale_completion` 0 → 1) came
  with no stall and no in-flight submit. That weakens the idea that the
  first-minute refresh caused the earlier stalls.
- A clean 10-minute run is about 37% likely by chance, so this run does not
  explain the stalls of soaks 002 and 003. The diagnostic stays in place for
  later soaks.
- The all-time best difficulty rose from 36,059 to 128,089 and never
  decreased.
