## Panic and recovery limits

The retained diagnostic export reports **boot16, reset_reason=panic,
uptime264ms**. It is marked non-authoritative diagnostic evidence; the cached
serial error is `timeout`. This establishes an observed new panic after the
boot15 admission. It does not identify the faulting frame, prove status caused
the panic, or establish the historical Share002 cause. No new core has been
read or decoded. Core partition contents remain untouched and unverified.

Independent read-only analysis reproduced a recovery orchestration defect:
`createPage.recoverFresh()` first requests the known attempt, before starting
independent ledger/budget collection. After reboot, firmware rejects a known-ID
query when the RAM record is absent. `readRecoveryStatus()` has no reboot-aware
recovery route; the failed logical session closes before independent reads.
A production-page simulation with that rejected status confirmed no ledger,
budget or diagnostics calls. This explains the evidence gap without proving
that physical restoration failed. The fresh reconnect briefly showed ready and
restored, but this UI observation is not a retained authenticated recovery proof.

The fixture also failed natural completion. Cleanup then terminated and reaped
its exact owner. The shared server aggregates the natural-completion failure
into `fixture-release.complete=false` even when termination succeeds. Exact
post-run checks found the server and fixture processes gone, the admitted serial
holder absent and the supervisor listener absent. The original sealed aggregate
release flags remain false; no historical result is rewritten.
