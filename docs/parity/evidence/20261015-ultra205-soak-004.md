# Ultra 205: upstream-default soak 004 after the publication-lock fix

Soak 004 attempt 001 passed on firmware that writes HTTP responses and the
WebSocket connect frame after the operator-snapshot lock is released. An
independent review agrees with `passed`.

The run showed no multi-second paired HTTP and WebSocket stall. As the review
found, however, it cannot credit that to the fix. Parity is not promoted.

## What this does and does not show

- The fix is correct for what it claims. Publications now only serialize
  under the lock, and socket writes happen after it is released. The
  cadence broadcast still only queues frames under the lock.
  `snapshot_io_ownership_tests` enforces this.
- ESP-IDF runs request handlers and queued WebSocket sends on one HTTP server
  task. Before the fix, the only lock holder that could be in a slow write was
  that task itself, and while it was blocked, HTTP and WebSocket delivery
  stalled anyway.
  - What the fix removes is other publishers (the telemetry cadence task, BAP)
    waiting behind a slow client.
  - It cannot remove a paired observer gap caused by a slow write on the server
    task, or by a Wi-Fi or TCP stall.
- Each earlier stall was a single event per soak, and the 2026-10-06 soak on
  the old code was clean. A clean 10-minute run is about 37% likely by chance,
  so this run is consistent with the fix but not evidence for it. The paired
  stall's cause is now `task-http-server-task-stall-diagnostics`.
- `stale_completion` stayed 0 for the whole run, so no clean-jobs notify
  overlapped a submit. The clean-jobs share-accounting fix's live path was not
  exercised; submitted equals accepted plus rejected.
